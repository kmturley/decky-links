# 🔗 Decky Links

**Launch games on SteamOS with physical media — NFC tags, floppy disks, QR codes and more.**

![Steam Deck with NFC tag reader](https://raw.githubusercontent.com/kmturley/decky-links/refs/heads/main/decky-links.jpg)

Decky Links is a [Decky Loader](https://github.com/SteamDeckHomebrew/decky-loader)
plugin for SteamOS that launches games when you present a physical object — tap a
tag, insert a disk, show a printed code. The launch URI lives *on the medium*, so
a disk paired on one Deck works on any other Deck running the plugin, as long as
the game is in that library. There is no database to keep in sync.

![Steam Deck with NFC cards, stickers and 3d-printed cartridges](https://raw.githubusercontent.com/kmturley/decky-links/refs/heads/main/decky-links-media-types.jpg)

Watch the demo: [youtube.com/watch?v=dVYhwyseCYk](https://www.youtube.com/watch?v=dVYhwyseCYk)

## Triggers

Each trigger is a *category* of hardware, not a specific device — swap ports or
replace a dead reader and your media keeps working. All are switched on and off
individually in the plugin panel, and a switched-off trigger does no work at all.

| Trigger | Medium | Default | Status |
| --- | --- | --- | --- |
| 🏷️ NFC | Tags, stickers, cards | **on** | Mifare Classic, NTAG21x, Ultralight; PN532 (UART), ACR122U, Proxmark, nfcpy |
| 💾 Floppy | 3.5" disks in a USB drive | **on** | FAT-formatted, payload in `decky-links.json` |
| 💿 Optical | CD / DVD | off | Same payload format |
| 💳 Memory Card | SD / microSD | off | Same payload format |
| 🔌 USB Storage | Thumb drives | off | Same payload format |
| 📷 Camera | Printed or on-screen QR codes | off | USB webcam; codes generated by the plugin |
| 📡 IoT | MQTT messages | off | Opt-in, optional shared secret |
| 📟 Serial | Line-delimited URIs | off | Opt-in |
| 📁 File | A watched directory | off | Opt-in |

Storage categories default to off unless the drive exists to *be* a trigger: a
floppy drive on a Deck was attached on purpose, while a USB stick usually holds
your own data, and mounting that uninvited is both a surprise and a delay.

## Features

- **Pair from the game page.** The link icon opens a modal listing your enabled
  triggers with a Pair button each, alongside a QR code for that game.
- **Per-trigger pairing.** With a tag on the reader *and* a disk in the drive,
  pressing Pair on the Floppy row writes the disk and leaves the tag alone.
- **Printable cards.** Two-sided 4×6" cards — Steam's box art on the front, a QR
  code on the back — saved to `~/Documents/decky-links` to print as covers or
  stickers.
- **Auto-launch** on presentation, and **auto-close** on removal. Only the medium
  that launched a game may quit it, so ejecting an unrelated disk does nothing.
- **Portable payloads.** `steam://run/…`, `steam://rungameid/…` (including
  non-Steam shortcuts) and `https://…`, validated against an allowlist backend-side.
- **Restricted mode with a physical key.** Register any medium as a key; take it
  away and the Deck locks down — see below.

## Restricted Mode

For handing the Deck to a child or a guest. Register a medium — a tag, a disk, a
USB stick — as the **key** from the plugin panel, and it behaves like a key left
in a lock:

| | |
| --- | --- |
| **Register a key** | Pick the trigger from the list; restricted mode is on from then on |
| **Key removed** | Locked |
| **Key present** | Unlocked |
| **Disable Key** | Restricted mode off, and the key is wiped from its medium |

Nothing is stored about which object it is, and nothing is stored about whether
the Deck is locked — being locked *is* the key being absent. There is no lock
switch to get out of step with the key, and a Deck that boots with the key in a
drawer comes up locked because the key is in a drawer.

The key is a random token written onto the medium, exactly like a game pairing,
so it works on any Deck you register it with and there is no database to keep in
step. One medium cannot be both a key and a game tag.

While locked:

- **Only games you hand it will run.** A game started by presenting a medium
  plays; a game started from the library is closed with a "Restricted title"
  notice. The allowlist is the box of tags and disks you leave out — there is no
  list to build and nothing to keep in step with your library.
- **Nothing can be written or configured.** Pairing, settings, formatting and
  the Mifare key tools are refused in the backend, not merely hidden.

A game already running when the key comes out is left alone, so locking
mid-session never costs anyone their progress.

Worth knowing for an NFC key: the tag has to stay on the reader to stay
unlocked, because that is what "the key is in the lock" means. Lift it and the
Deck locks. A disk or USB stick suits an admin session better — it sits in the
drive while you work and locks the Deck when you pull it out.

### What it does not do

Steam's own menus stay reachable: the Store, Steam Settings and Desktop Mode are
not blocked. Valve's only per-account restriction that can bind the account
holding the library is **Family View**, its older PIN-protected mode — and Steam
no longer offers to set that up on an account that never had it. Its replacement,
Steam Families, applies its controls to *child* accounts, which is the opposite
of what a shared Deck needs: the games are in the parent's library.

If your account does still have Family View, Decky Links locks it alongside its
own lock, and the panel shows a Manage row. Store its PIN there and the key
unlocks Family View too; leave it empty and Steam's own prompt is the way back
in.

Losing the key means editing `settings.json` in Desktop Mode to clear
`restricted.key_hash` — there is no PIN of our own, deliberately, since a second
way in is a second thing to leave switched on by accident.

Restricted mode is a guardrail for a shared living-room device, not a security boundary.
A restricted game does visibly start before it is closed, and anyone who can read
the medium can copy it.

## Decky Links vs Zaparoo

[Zaparoo](https://zaparoo.org) is a cross-platform "universal loading" system
supporting Windows, Linux, SteamOS, MiSTer, Batocera and more, with a Designer
app, scripting API and a wide range of readers.

Decky Links is deliberately narrower: SteamOS only, with deeper Steam
integration. It uses Steam's native URI launch and quit behaviour, so there is no
separate service to install and no library index to maintain.

Choose Zaparoo if you need one solution across several devices, or want advanced
rules and APIs. Choose Decky Links if you want a lightweight, Steam-native
launcher on a Deck.

## Architecture

Each trigger is a `MediaSource` running its own asyncio task at its own interval,
pushing into a shared queue that the plugin's event loop consumes. Adding a
trigger means adding a source, not touching the state machine.

```
                      ┌──────────────────────────┐
                      │      Plugin (main.py)    │
   ┌──────────────┐   │  state machine, launch,  │   ┌──────────────┐
   │ SourceManager│──►│  pairing, media registry │──►│  Frontend    │
   └──────┬───────┘   └──────────────────────────┘   │  events      │
          │                    ▲                      └──────────────┘
          │            shared asyncio.Queue
   ┌──────┴───────┬───────────┬──────────┬───────────┐
   ▼              ▼           ▼          ▼           ▼
NfcSource   StorageSource  Camera     Mqtt      FileWatch
```

Two event types flow through the queue: **`SourceEvent`** for hardware coming and
going, and **`MediaEvent`** for media being presented, removed, or still being
read. Media is tracked *per source*, so a tag and a disk can be present at once
and each has its own state in the UI.

### Repository layout

| Path | What |
| --- | --- |
| `main.py` | Plugin backend: state machine, launch/quit, pairing, RPCs |
| `sources/` | One module per trigger, plus the `MediaSource` base and `SourceManager` |
| `nfc/` | Reader backends and tag handlers (Mifare, NTAG, Ultralight …) |
| `cards/` | QR code and printable card generation |
| `src/` | Decky UI: panel, game-page modal, background event listeners |
| `src/lib/triggerRows.ts` | The trigger row model shared by the panel and the modal |
| `tests/` | Python tests (650+) |
| `docs/hardware-test.md` | Ordered manual test plan for a real Deck |
| `SPEC.md` | v1 behaviour spec — state machine, launch rules, error handling |

## Developer setup

### Prerequisites

- Node.js ≥18 and `pnpm`
- Python 3 with `venv` (for the test suite; any recent version)
- Docker, for building the plugin zip
- A Steam Deck with Decky Loader, for anything hardware-related

### Install

```bash
pnpm install

python3 -m venv .venv
.venv/bin/pip install -r tests/requirements.txt pytest pytest-asyncio Pillow
```

### Build

```bash
pnpm build            # frontend only, into dist/
./.vscode/build.sh    # full plugin zip into out/
```

`build.sh` vendors Python dependencies into `py_modules/` using a
`linux/amd64` container, because the Deck is amd64 and host wheels will not load
there. It also copies `sources/`, `nfc/`, `cards/` and `assets/` into
`py_modules/` — the packaging CLI zips a fixed allowlist that does not include
them, so anything left at the top level never reaches the device.

> [!IMPORTANT]
> **`DECK_PYTHON` must match the interpreter Decky Loader runs plugins with, not
> the one SteamOS ships.** The loader is a frozen binary carrying its own Python
> (3.11.7 as of 2026-08) while SteamOS is on 3.13. Building against the wrong one
> ships extensions that fail to load, silently disabling the camera and storing
> NFC keys unencrypted. The plugin logs the answer at startup:
>
> ```bash
> pnpm logs | grep -A4 "Python runtime"
> ```
>
> Re-check after any Decky Loader update. The build guards both version-tagged
> and abi3 extensions against `DECK_PYTHON` and fails loudly on a mismatch.

### Deploy and debug

```bash
pnpm deploy           # rsync the tree to the Deck
pnpm deck:restart     # restart plugin_loader — required, see below
pnpm deck:status      # devices, mounts, plugin process, dependency imports
pnpm logs             # tail the plugin log
pnpm logs:follow      # …live
pnpm deck:udev        # watch block-device events live
```

A deploy alone is not enough: the plugin's uid is fixed when its process spawns,
so mounting disks needs a loader restart to take effect. `deck:status` reports
`STALE` when the deployed files are newer than the running process.

### Testing

```bash
pnpm test                              # the whole suite
.venv/bin/pytest -q tests/test_plugin.py
```

Three dependency-import tests fail on a non-Linux dev machine (`pyudev`,
`paho-mqtt`, `zxingcpp`); they pass on the Deck. Everything else runs anywhere.

For hardware, work through [`docs/hardware-test.md`](docs/hardware-test.md) — ten
ordered steps with commands and pass criteria. The order matters: a stale deploy
or a leaked mount makes every later result meaningless.

## Security

- URIs are validated backend-side against a strict allowlist: `steam://run/*`,
  `steam://rungameid/*` and `https://` only. The same check gates launching,
  pairing and QR generation.
- Settings are validated before being persisted, and again when loaded from disk.
- Virtual triggers (MQTT, serial, file watcher) are **off by default** and
  opt-in; MQTT supports a shared secret.
- Mifare Classic writes skip trailer blocks, so keys and access bits cannot be
  corrupted.
- Writes are refused before the first byte when a tag is too small for the
  payload, so a failed pair leaves the previous value intact.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Panel shows nothing / stale state | `pnpm logs` — the plugin emits status on change and on a 2s tick |
| `must be superuser to use mount` | The loader did not restart; `pnpm deck:status` shows the process user |
| Camera never connects | `pnpm deck:status` import check, and the `Python runtime` note above |
| Reader not detected | Auto-detection only matches known USB-serial vendor IDs; set the device path in settings |
| Drive letter drifts `sda`→`sdb` | A leaked mount is pinning the node — `grep decky-links /proc/mounts` |
